# Listful Thinking review — 2026-09-26

Reviewed `main` at `7778df4352237b329d4748c44823d74ca177da59`. Scope: standalone Docker application, frontend, backend, tests, deployment, and documentation. No application fixes were made during this review.

## Assessment

The product has a useful foundation: centralized list authorization, separate public DTOs, BCrypt passwords, hashed bearer tokens, atomic guest claims, database migrations, SSRF defenses, a non-root container, and meaningful backend tests. Keeping the current architecture is reasonable. The next investment should be reliability and usability rather than another platform migration.

The highest priorities are authentication/session lifecycle, shared-user workflows, audit redaction, and trustworthy release checks. Passing tests currently overstate confidence in complete user journeys.

Priority: **P1** = address first, particularly before wider/public use; **P2** = next reliability/usability work. “Reproduced” means observed against the isolated local review instance; “source-confirmed” means established from implementation, without a complete runtime reproduction.

## P1 findings

### 1. Login and registration preserve the anonymous session ID — reproduced

Source: `backend/src/main/java/app/listful/auth/SessionAuthentication.java:15`.

Request `/api/v1/auth/csrf` to obtain an anonymous session, then register or log in using that cookie. The `JSESSIONID` remains unchanged in both cases. The authentication helper writes directly into the existing session without rotating its ID or invoking the session authentication strategy.

This creates the session-fixation precondition: if an attacker can arrange for a victim to authenticate in a session the attacker knows, the identifier remains usable. This review did not demonstrate a browser delivery mechanism for planting that cookie.

Fix: use Spring Security's authentication/session strategy or explicitly rotate the session at successful authentication, covering registration and magic-login too. Test that the prior identifier cannot access the authenticated account. See [Spring's session-management guidance](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html).

### 2. Password reset leaves existing access valid — reproduced

Sources: `backend/src/main/java/app/listful/auth/AuthService.java:139`, `backend/src/main/java/app/listful/auth/ActiveUserSessionFilter.java`.

After a successful reset (HTTP 204), a previously authenticated session still returns HTTP 200 from `/auth/me`. A magic-login token issued before the reset also still authenticates successfully. Reset only changes the password hash; the active-user filter checks account activation, not credential changes.

Fix: invalidate existing sessions and outstanding recovery/login tokens when a password is reset. A per-user credential/session version is one option that does not require adding another service. Add a recovery test with two sessions and outstanding tokens.

### 3. Public bearer tokens leak through security audit paths — reproduced

Sources: `backend/src/main/java/app/listful/config/SecurityHardeningFilter.java:219`, `backend/src/main/java/app/listful/security/SecurityAuditService.java:19`.

Send an oversized request to `/api/v1/share/{token}/items/{id}/claim`. It correctly returns 413, but the resulting `security_events.path` contains the complete raw token. The audit logger also logs the same path. Thus, hashing the token in the lists table does not keep the token out of the database and logs.

Fix: normalize/redact sensitive route parameters before both persistence and logging. Add a test that searches audit output/storage for the submitted token. Review existing audit retention and rotate affected links where necessary.

### 4. Shared users appear logged out when refreshing — reproduced in browser

Sources: `frontend/src/App.vue:487`, `frontend/src/App.vue:618`, `frontend/src/App.vue:708`, `backend/src/main/java/app/listful/sharing/ListSharingService.java:31`.

A user with a contributed list can fetch its items (200), but fetching its sharing roster correctly returns 404 because that endpoint is owner-only. The UI requests both unconditionally. During startup, the error propagates into the broad catch block, which sets `currentUser` to null.

Reproduction: create a user with only a contributed list, log in, and refresh. The login form appears even though `/api/v1/auth/me` still returns 200. Initial login also encounters the failed sharing request.

Fix: load the share roster only for owners. Treat a detail-loading error separately from an authentication failure; clear obsolete data and show a local retry/error state. Test owner, reader, and contributor startup in real separate browser contexts.

### 5. Backup instructions can produce an inconsistent backup — source-confirmed

Sources: `docs/deployment/self-hosting-handbook.md:146`, `README.md` data/backup section.

The handbook recommends plain `cp` and explicitly allows copying from a running container, without obtaining a consistent database snapshot. It also lacks a complete restore-and-verify procedure. This puts the user's only copy of household data at risk during recovery.

Fix: document either stopping the application before copying, or using SQLite's online backup mechanism. Include restoration into an isolated instance, integrity checking, and a login/list verification. SQLite documents the risks of copying during a transaction and its [online backup API](https://sqlite.org/backup.html); see also [SQLite corruption guidance](https://www.sqlite.org/howtocorrupt.html).

## P2 findings

### 6. Mutations fail after logout/login without a page reload — reproduced over HTTP; client cause confirmed

Source: `frontend/src/api/client.ts:216`, authentication functions at lines 341 and 362.

The module caches a CSRF token, but neither logout nor login clears it. Logout destroys the server session. Sending the old cached token after logging in again returns 403. The same lifecycle issue needs consideration for expired sessions and account switches.

Fix: clear cached CSRF state at authentication boundaries; handle a recognized CSRF rejection by refreshing the token with a bounded retry. Test login → create → logout → login → create using the real API client.

### 7. Duplicate email addresses break account recovery — reproduced

Sources: `backend/src/main/java/app/listful/auth/AuthService.java:106`, `backend/src/main/java/app/listful/auth/AuthService.java:150`, `backend/src/main/java/app/listful/domain/User.java:26`, `backend/src/main/java/app/listful/domain/repository/UserRepository.java`.

Creating two users with the same email succeeds (201). Requesting password recovery for that address then returns 500: `findByEmail` expects at most one result, while storage and creation permit multiple results. Magic login uses the same lookup.

Fix: decide whether one email identifies one account. If yes, enforce normalized uniqueness in validation and the database, with a migration plan for duplicates. If shared family email addresses are intended, recovery must identify the specific account instead. Preserve non-enumerating responses.

### 8. Full container smoke testing is broken and not executed by CI — reproduced

Sources: `scripts/smoke.sh:139`, `.github/workflows/ci.yml:9`, `backend/src/main/resources/application.yml`.

The script sends a roughly 70 KB body and expects the payload-limit response 413. The current default limit is 5,100,000 bytes, so authentication runs instead and returns 401. The script stops there; its later workflows are not verified.

CI checks the script's textual contract and runs GUI smoke tests, but does not execute this complete smoke script. Consequently both the contract and CI-style suites can pass while the documented release verification fails.

Fix: explicitly configure a test body limit or derive the oversized fixture from the configured value. Execute the full smoke script in CI/release verification and keep the contract test as a separate check.

### 9. Mobile layout overflows, and routine controls are buried — browser-confirmed

Sources: `frontend/src/assets/main.css:117`, `frontend/src/assets/main.css:162`, `frontend/src/assets/main.css:257`, `frontend/src/App.vue:82`.

At a 390 px viewport, document width measured 475 px. The admin user rows remain flex rows on mobile while several other lists switch layouts; their contents and grid minimum sizing contribute to overflow. The large introductory header and expanded account/user inventory precede the user's working lists. On desktop, the list column also stretches cards into large empty blocks alongside the detail panel.

Fix: put administration behind a dedicated view or collapsed control; reduce the persistent header; use a compact list navigator; constrain grid children with appropriate minimum sizing and wrapping. Add a no-horizontal-overflow assertion with realistic users, emails, long titles, and populated lists. Visibility assertions alone do not establish mobile usability.

### 10. Public links disappear from the owner UI after reload — reproduced; documented design tradeoff

Sources: `backend/src/main/java/app/listful/domain/ListEntity.java` transient token field, `backend/src/main/java/app/listful/sharing/PublicShareService.java:40`, `frontend/src/App.vue:203`.

After creating a link, a subsequent list GET returns `publicList: true` but `shareToken: null`. Hash-only storage deliberately prevents retrieving the original secret. The UI gives little explanation: the displayed URL disappears, and “Create public link” remains available. Creating again rotates the link and invalidates URLs already distributed.

Fix: retain hash-only storage and make the one-time display explicit, with copy/open controls, a clear “link active” state, and a separate warned “replace link” action. Add reload and rotation UX tests. This limitation is already described in `docs/architecture/security.md:84`, but the user flow does not communicate it.

### 11. Changing a populated list's type leaves incompatible items — reproduced

Sources: `backend/src/main/java/app/listful/lists/ListService.java:51`, `backend/src/main/java/app/listful/items/ItemService.java:132`.

Create a purchased wishlist item with URL and price, then change the list to GROCERY: the update returns 200 and the item remains PURCHASED with shopping fields. Updating it with the normal full item payload then returns 400 because grocery validation rejects those fields.

Fix: prevent type changes for populated lists until there is a deliberate conversion workflow, or migrate incompatible fields/statuses atomically and explain any losses before conversion.

### 12. Collaboration can silently overwrite newer item data — source-confirmed

Sources: `frontend/src/App.vue:985`, `backend/src/main/java/app/listful/items/ItemService.java:64`, `backend/src/main/java/app/listful/domain/Item.java:96`.

Even a Done toggle sends the full locally cached item. Updates replace all fields, and items have no revision check. If another household member changes the name, quantity, or notes after the first browser loaded the list, a later status toggle can overwrite that change.

Fix: use targeted status mutations plus optimistic version checks for edits. Add a two-client stale-edit test that verifies a conflict or preserves unrelated changes. Consider refresh-on-focus/polling separately; it does not replace concurrency protection.

### 13. URL import can remain “Loading metadata…” indefinitely — source-confirmed

Sources: `backend/src/main/java/app/listful/items/ItemEnrichmentService.java:30`, `frontend/src/App.vue:893`.

Import failure is logged but leaves the placeholder name in storage. The browser performs only one delayed reload after 1.5 seconds, while the scraper allows substantially longer network waits. Successful slow imports can therefore also look unfinished until another reload. A background result does not verify that the item's URL is still the one originally scraped.

Fix: represent import state explicitly, show a usable fallback name and retry/edit action, poll until completion with a deadline, and verify the URL/revision before applying metadata.

### 14. Reminder scheduling misses some due items — source-confirmed

Sources: `backend/src/main/java/app/listful/notifications/ReminderService.java:45`, `backend/src/main/java/app/listful/domain/repository/ItemRepository.java:33`.

The job runs once daily at 06:15 and selects only items due in the following 24 hours. An item created at 10:00 and due at 18:00 that day is outside the next run's window. Downtime during the daily run likewise has no catch-up mechanism. SMTP successes do not persist a delivery marker, so repeated processing of the same window is not idempotent for email.

Fix: define reminder timing and timezone semantics, run frequently enough to meet them, persist delivery identity/status, and add catch-up plus duplicate-delivery tests. Existing tests call the service directly with fixed times and do not exercise the scheduling gap.

## Additional UX, maintainability, and operational work

- **Accidental deletion:** item deletion and grocery “Clear completed” execute immediately (`App.vue:954`, `:961`), unlike list deletion. Add undo or a proportionate confirmation for destructive actions.
- **Request feedback:** `run()` only sets a page-level message. There are no per-action pending guards, so double submissions and overlapping updates are possible. Errors at the top are easy to miss after scrolling. Add local pending/error states and focus management.
- **Currency correctness:** the scraper returns `priceCurrency`, but persistence/UI drop it and display `€` (`App.vue:26`, `:330`, `:822`). A non-EUR product price is mislabeled; zero prices are hidden by truthiness. Store currency and format with locale-aware currency output.
- **Localization and semantics:** raw `WISH`, `TODO`, `OPEN`, and `CLAIMED` values and ISO timestamps are shown to users. Several select labels remain English. Use translated names and formatted dates; expose selected-list state accessibly.
- **Editing notes:** non-wishlist item edits send `description: undefined` (`App.vue:973`) although the API accepts descriptions. Editing an API-created item with notes can erase them. Preserve hidden fields or expose the notes field consistently.
- **Payload growth:** pasted images are stored as data URLs and included in unpaginated item responses. A modest list of large photos can produce tens of megabytes of JSON. Store media separately, generate thumbnails, and introduce bounded list retrieval as usage warrants.
- **Frontend structure:** `App.vue` combines authentication, admin, list management, sharing, imports, notifications, and item workflows in 1,056 lines. Split by workflow after adding regression tests for the identified boundary bugs; avoid a rewrite for its own sake.
- **Operational health:** `/api/v1/health` returns a constant status and does not verify database access. Keep liveness lightweight, but add a readiness/database check and a restore verification procedure.
- **SMTP:** documented port-587 settings omit explicit authentication/STARTTLS and sender configuration. Verify against a representative submission server and document supported environment settings; actual mail delivery was not tested here.
- **Security follow-up:** replace the broad custom CSRF exceptions with an explicit authentication model; review per-account/per-instance abuse limits and audit retention. URL-enrichment jobs triggered by item creation bypass the dedicated scrape endpoint's rate limit. These deserve bounded workload tests, not an assumption that endpoint rate limiting covers all scraping.

## Documentation corrections

- `docs/architecture/security.md:79` correctly describes hashed tokens, but its deferred-hardening section at line 118 still says they are stored raw. Its audit backlog also predates implemented admin/share events.
- The current-state register contains historical passing smoke evidence; it should distinguish historical results from the current failing checkout and reflect subsequent implementation changes.
- The handbook's general update command uses default Compose even though its recommended deployment uses `compose.prod.yml`. Provide profile-specific update commands so an operator does not inadvertently use another volume or port binding.
- Public link construction in the frontend uses `window.location.origin` (`App.vue:821`); the troubleshooting advice to change `PUBLIC_BASE_URL` will not change that displayed URL. Clarify the difference between browser-generated share links and server-generated email links.
- Link/contract checks establish document structure, not the correctness of operational advice. Add executable verification for backup/restore and release instructions where feasible.
